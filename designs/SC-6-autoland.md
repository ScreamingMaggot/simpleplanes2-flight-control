# SC-6 自动降落（纯 FT）设计规格

目标：在 `TESTaircraft2` 上用**纯 Funky Trees**复刻 SC-3b 的进近落地（横向压线 + 纵向下滑 + 拉平），不依赖 Lua。
前提（已实飞验证）：姿态电传 v0.1、高度环 v0.7（**VTOL=高度窗**）、航迹环 v0.8（**出生点+出生方向=跑道线**）。唯一真源 `analysis/scripts/ft_ta2_patch.py`。

## 0. 架构原则（用户约束："VTOL 现在直接和高度有映射，避免逻辑冲突"）

**只保留一条高度链，自动降落不另开第二套垂直律**：

```
高度目标来源（二选一/仲裁） ──► vsCmd = clamp(k·(altTgt−Alt), ±vsLim)  ──► vsInt ──► cmdThe（含失速门）
        ▲                                     （v0.7 已验证的整条链，全部复用）
   ├─ 手动：altTgt = f(VTOL)   分段线性 2000/500/0 m（飞行员旋钮）
   └─ 进近：altTgt = 场高 + 0.0524 × max(dist − 瞄准点偏移, 0)        （下滑道 3°）
```
**VTOL 的用法**：进近期间 VTOL 旋钮仍然有效，作为**"上限"**参与仲裁（见 §3 决策 1）；**螺旋桨 IC 在 8 号接通时归律**（推力管理），此时 VTOL 不再驱动桨距 —— 这正是"避免 VTOL 一脚踩两条船"的冲突点，此设计把它掰开：**8 开=VTOL 是高度窗、桨归律；8 关=VTOL 回桨距、全手动**。

## 1. 横向（已有，直接用）

航迹环已把"出生点 + 出生机头方向"钉成一条线 ⇒ **就是跑道延长线**。
- 起飞方向与落地方向相同时：进近从远侧沿同一方向切入，环自然对正（`trkErr=180°` 时它会先掉头，符合"对准跑道方向"意图）；
- 反向着陆（要飞 180° 进近）：**手操对正后松杆**重新抓一次（`fol` 机制允许）。
- 横偏读数 `X`（Label 42）就是"离中线多少米"⇒ 落地判据直接用它。

## 2. 纵向（新建，复用高度环）

### 2.1 场高 `elev` 的合法来源（用户订正）

⚠ **禁止**：飞行中用 `Altitude − AltitudeAgl` 反推场高 —— 它给的是**正下方地形**的高度（脚下可能是山谷/树线/水面），与跑道标高无关。
合法来源只有两个：
1. **烘焙表**：`runway-locations.json` 每条跑道自带标高（如 Kunimitsu 19 = 10 m）⇒ B/C 方案用这个；
2. **出生瞬间冻结**：出生点就在跑道上，那时读一次 `Altitude − AltitudeAgl` 并**冻住**（`fol` 那套同一机制）⇒ A 方案用这个，零成本但要保证出生在跑道上。


| 量 | 式 | 说明 |
|---|---|---|
| `elev` | 来源见 §2.1 | **跑道标高**（不是"正下方地形高"！） |
| `dist` | `sqrt((Lat−latTgt)² + (Lon−lonTgt)²)` | 到**瞄准点**的斜距（水平近似；低速小角度下够用） |
| `altProf` | `elev + 0.0524 × max(dist − dAim, 0)` | 3° 下滑道；`dAim`=瞄准点相对出生点的前移量 |
| `altTgt` | 见 §3 决策 1 | 手动=VTOL 映射；进近=剖面 |
| `vsCmd/vsInt/cmdThe` | **原样复用 v0.7** | 不新写垂直律 |
| 拉平 | `agl < 15` ⇒ `cmdThe = max(cmdThe, 6)`；推力收到 0 | 参考 SC-3b「拉平必收光油门」 |

## 3. 三个待定决策（我给了推荐值，你点头或改）

**决策 1：进近时谁说了算（避免与 VTOL 冲突的方式）**
- **A（推荐）**：`altTgt = min(f(VTOL), altProf)` —— VTOL 变成"**不得高于**"的上限旋钮；剖面只在进近窗内生效。好处：飞行员随时可以把目标往下压（早下高），不会与律打架；坏处：想临时飞高必须关 8。
- B：模式切换 —— `进近窗内 altProf 完全接管`（VTOL 被忽略）；简单，但飞行员失去临时干预。
- C：两个都做成"取更保守者"（高者优先）—— 与 A 相反，倾向于一直飞高，不适合进近。

**决策 2：瞄准点 `dAim`（相对出生点的前移量）**
- **推荐 0 m**（瞄准出生点=跑道头；出生点一般在跑道起点附近）；
- 或 250 m（落地前多飞一段，接近现实"接地区"）。
  - **订正（用户指出后核实）**：我原写"纯 FT 拿不到跑道数据"是错的——
    ① **标高不用表**：`Altitude − AltitudeAgl` 在地面读一次即得（任何机场通用）；
    ② **阈值点/航向我们有表**：`analysis/data/runway-locations.json`（**17 条**跑道：lat/lon/航向/标高），SC-5 就是拿它烘的 13 条走廊，且 SC-5 已验证"面板 100+ 条 setter 可行"；
    ③ **长度**：表里没有，但**反跑道两端阈值一减即得**（如 Kunimitsu 1↔19 ≈ 1056 m）；且 SC-3b 的落地基准是"瞄准点=阈值前 250 m"，**长度非必需**。
    ⇒ 所以瞄准点既可以"相对出生点"（零成本），也可以"相对烘焙阈值"（多机场 + 精确）。

**决策 3：进近窗与接入条件**
- 推荐：`dist < 8000 m` → 剖面生效；`dist < 150 m` 或 `agl < 3` → 交还手动（落地/滑跑）；
- 是否要求"先对准（`|X| < 300 m`）才接入"？推荐**不要求**（让环自己去收），否则又回到"接杆资格"那套。

## 4. 推力/速度（用 SC-5 的血账：**推力阀门在螺旋桨 IC**）

- `PROP = GATE ? 推力需求 : VTOL`（8 开=律管桨，8 关=VTOL 回桨距）；
- 速度目标（进近）：`VSP = 65 + 20 × clamp(dist / 6000, 0, 1)`（远快近慢，65 m/s≈本机 1.1Vs 量级）；
- 油门律：`clamp(0.35 + 0.05×(VSP − IAS), 0, 1)` + **拉平收光**（`agl < 15` ⇒ 0）；
- ⚠ 本机推力弱（持续爬升仅 ~5.5 m/s），**下滑必须靠能量换**，所以进入剖面时"高于剖面"要允许大下沉（`SSK` 式的速度分级下沉上限，SC-5 已验证的写法）。

## v1 已实现（表驱动，2026-09-25）

**方案 C 落地**：把 `analysis/data/runway-locations.json` 的 **13 条真跑道**（阈值点/航向/标高，Lua 时代从地图硬标）搬进 FT 面板，脚本 `ft_ta2_patch.py` 里由 `load_runways()` 生成（唯一真源=那张 JSON）。

面板 **114 条**（与 SC-5 验证过的 113 条同量级）：
`boot/cmdPhi/vs/airb/hold/RCAP/vsLim` → 每跑道 `SDi/LTi/Gi` → 逐级选择链 `QSi/QLi/QTi/QDi`（最近者）→ 别名 `SD/LT/TLA/HDG` → 消费 `trkNow/trkGd/trkUse/xtrk/trkEr/bankTrk/altTgt/vsCmd/vsErr/vsInt/cmdThe/phiCmd`。

- **横向**（自动降落压线）：`xtrk = LT`（表里选出的横偏，米，正=中线左）、`trkEr = deltaangle(trkUse, HDG)`（对**跑道航向**做误差），`bankTrk = -clamp(trkEr + clamp(0.15·xtrk, ±20), ±30)` ⇒ 直接把飞机压到中线；走廊外用 0（不做修正）。
- **纵向**（下滑剖面）：`altTgt = min(VTOL映射, 走廊内 ? 场高 + 0.0524·SD : 9999999)` —— **VTOL 是"不得高于"的上限旋钮**，剖面只在走廊内生效；下游 `vsCmd → vsInt → cmdThe`（含失速门/空中门）全部沿用验证过的件。
- **道线**：3°（0.0524）过阈值、场高取自表。

**v1 未做**（下一版）：① **推力接管**（螺旋桨 IC：`PROP = GATE ? 需求 : VTOL`，SC-5 血账：推力阀门在桨上）；② **拉平**（`agl<15` 抬高姿态指令 + 收光油门）；③ 瞄准点前移（现为"过阈值"，若要接地区再加 250 m）。

## v1.2：转弯提前量按转弯半径 + 自动放轮/自动刹车（用户 2026-09-25 要求）

**横向前置角改成"按转弯半径算"**（用户点名做法，替掉 v1.1 的 SC-3b 双调度）：
`Rturn = GS²/5.66`（30° 坡的协调转弯半径，g·tan30°≈5.66）、`LEAD = clamp(atan(xtrk / max(400, Rturn)), ±45°)`。
物理含义：**看向"正前方 R 处的中线点"**——快则 R 大、前置角温和；慢则 R 小、转得紧；对准时 atan(0)=0 自动归零。
（400 m 地板防低速时 atan 爆掉；±45° 与旧双调度的 ±40° 同量级但**保证渐近**。）

**自动刹车 = 真律**（用户定则：`Brake` 是一个输入变量，喂三个轮子（地面起效）+ 一对减速板（空中起效））：
`BRAKE_EXPR = (Activate8 & (airEver > 0.5) & (SD < 3000) & (AltitudeAgl < 8)) ? 1 : Brake`，写在**轮件 IC#1**（`JWheelAssembly` ×3）。
- 假分支给裸 `Brake` ⇒ **手动刹车照旧**；关掉激活组 8 即完全回到手动（失效安全 + 落地后想滑行的开关）。
- **`airEver` 升空锁**是必需的：出生就在跑道上，`AGL<8 & 近场` 与"落地滑跑"长得一模一样——没有这把锁，开机第一秒满刹车压在轮上，油门再大也起不来（且不可复现）。
  `airEver = clamp01(sum((AltitudeAgl > 30) ? 1 : 0))` —— 用 `sum()` 的积分记忆当一次性锁存（面板不能自参照，这是唯一合法路径）。
- **减速板那一对故意不写**（三条理由，不是"怕不能改"）：① 同一把变量会让减速板在 AGL<8 张开，那正是拉平段，凭空多阻力而**油门还没自动化** ⇒ 下沉更陡、硬着陆；② 短五边会把飞行员的手动减速板抢走（功能倒退）；③ 空中用阻力得等 v2 有油门权限。

**自动放轮 = 实验（`--landtest`）**：`GEAR_EXPR = ((SD < 3000) & (AltitudeAgl > 5)) ? 0 : LandingGear`，写在 `GearLeg`×3 + `GearBay`×1。
- 假分支 = `LandingGear` ⇒ **远场退化成原厂**，起飞/巡航绝不受影响；签名 = 进近 3 km 内**手柄打到收上、轮子自己放下**（与手动相反的指令才算证据，SC-5 §32"只认裸轴名"的判决重开）。
- 判读表：自己放下 ⇒ 零件 IC 执行表达式，§32 作废、自动放轮纯 FT 成立；全程照手动 ⇒ §32 维持，放轮改走窄口 Lua `OverrideInput`；**连手动都卡死** ⇒ 表达式编译失败、IC 值不更新。

**工具侧两条**（本轮真踩）：① 控制台 GBK 编码不了 `✓/⇒`，崩在**收尾 print** 上——而文件其实已经写完了，是最阴的假失败 ⇒ `sys.stdout.reconfigure(errors="replace")`；
② `"不碰"必须写成"显式还原成裸轴名"`——改完 `BRAKE_CHANNELS` 只跑轮子后，减速板上一次试验的式子**原样留在盘上**（静默）。刹车通道改按 **IC 序号**定位（轮 #0=Yaw、#1=Brake）+ 旧值守卫（只认裸轴名或本工具写过的式子），防设计器改结构后写错通道。

**待查（写给 v2 的坑）**：本机螺旋桨 IC（id=9）吃的是 **`VTOL` 轴**且挂在**激活组 8** 下，而 `altTgt` 也用 VTOL ⇒ 存在**"高度窗旋钮同时改推力"**的疑点。飞行中做一次对照（**油门不动、只推 VTOL 旋钮**，看转速/推力是否跟着变）即可定案；v2 推力接管本来就要显式写这条 IC，写下去就顺带解掉这个耦合。

## v1.7：起落架谜案结案 = 反编译实读（不是猜，也不是"平台不吃表达式"）

**用户第三次报障**："还是不放起落架"。离线重放这一局（COBS 解码 + 走廊重放，`trace_landing.py`）：
条件**完全成立**——t=105~165、SD 2951→133、AGL 157→7，我的式子全程输出 `+1`，而轮子没动。
把三次架次的观测串起来（写 `0` 看不到动作 / 写 `−1` 用户看到"自己收起来了" / 写 `+1` 没反应），
只剩一个自洽解释。**去反编译 Game.dll 一读，两条铁证**：

**① `InputControllerScript.UpdateValue()` 的真身**（ilspycmd 实读，原文）：
```csharp
if (num < 0f) Value = (0f - num) * InputController.MinValue;
else          Value =           num * InputController.MaxValue;
```
⇒ **`MinValue`/`MaxValue` 是两条独立的乘数，不是"把 `[-1,1]` 映射到 `[min,max]` 端点"**！
见 `analysis/ft-documentation-notes.md` 同款记载；对起落架这类 `min=1 max=0` 的件：

| 写入 input | 乘谁 | Value | 语义（leg） |
|---|---|---|---|
| `−1` | MinValue = 1 | 1 | **收起** |
| `0` | MaxValue = 0 | 0 | **放下**（原厂默认态） |
| `+1` | MaxValue = 0 | 0 | **死值**（与 `0` 等价） |

⇒ **这类件只有 `−1` 和 `0` 两个有效值；`0` 本来就已经是"放下"。** 四次写入的正解是 `? 0`——
**正好绕回我 v1.2 的原始写法**，而我当时把它误读成"0.5 半值"改掉了，一路错到 v1.6。

**② `RetractableLandingGearScript.OnUpdate()`**（同一处实读）：
```csharp
AnimateLandingGear(base.PartScript.Aircraft.Controls.LandingGearDown);   // 收放动画只认**控制轴**
base.LandingGearEnabled = base.PartScript.Aircraft.Controls.LandingGearDown;
```
⇒ **`GearLeg` 的零件 Value 根本不进收放动画**，它只改 `WheelCollider.SuspensionEnabled`（悬挂/承载）。
所以"腿部零件"和"控制轴"是两套互不相干的通道：**零件 Value 只能阻止腿收起（=`0` 锁在放下）并让悬挂生效，
做不出"从收起到放下"的收放动作**——这也解释了为什么 SC-5 当年试遍表达式都"没反应"（那时机构本来就在放下态）。

**v1.7 定版**：
- 放轮：`((SD < 3000) & (AltitudeAgl > 5)) ? 0 : LandingGear`（+ 远场回裸轴名）。**只阻止收起、永不主动收起** = 零地面风险。
- 刹车不变（`min=0 max=1` 标准型，`+1` → 满刹，SC-3 v4.6 已验）；式子里去掉 `SD` 条件的修正保留。
- **减速板改成"替身指示"**：`AirBrake` 也是标准型，近场张开 ⇒ 既是一个"构型已就位"的可见标志，
  也是个能用的减速手段（用户嫌难看就把那一行换回 `"Brake"` 一行还原手动）。
- **Label 39 改成门控显示** `LG {FLAP|GATED|--}`（不是飞机真实状态）。要显示真实状态得启用轮件的
  `Suspension`/`Extension` 输出（需在部件的"部件变量"菜单里命名，本机还没做——**下一步可选**）。

**方法论教训（这条最贵）**：三次失败我都用"观测到的现象 + 直觉映射"去反推量程，
**而正确做法是去读那 40 行源码**。`InputControllerScript` 就在 Game.dll 里、`ilspycmd` 就在 `tools/` 下——

**文档这句话本身是误导性的简化**，源码才是权威。

## v2.0 能量环（用户授权：油门 + 空中减速板）

**"这俩不能打架"的解法不是协调，是在空速轴上分区、互斥、留死区**（SC-3b v4.8 同族教训）：

```
VAPP = 55                                   # 五边目标表速（本机成功局接地 41~45、超速局冲到 77）
thrFly  = clamp(Throttle + 0.06*(VAPP-IAS), 0, 1)      # 以飞行员盘位为基线的 P 律（无积分 ⇒ 不会 windup）
airFly  = ((airEver>0.5) & (AltitudeAgl>=3)) ? 1 : 0   # 已升空过且在 3 m 以上
gndIdle = ((airEver>0.5) & (AltitudeAgl<3))  ? 1 : 0   # 接地即收光（retard）
thrCmd  = airFly*thrFly + (1-airFly)*(1-gndIdle)*Throttle   # 乘式拼三段（不赌嵌套三元语法）
spdBrk  = ((airEver>0.5) & (AltitudeAgl>100) & (SD<15000))
          ? clamp(0.08*(IAS - VAPP - 12), 0, 0.4) : 0
零件：发动机 = GATE ? thrCmd : Throttle ；减速板 = GATE ? max(spdBrk, Brake) : Brake
```

**互斥性是可算的，不是祈祷的**：`IAS ≥ VAPP+12 = 67` 时 P 项 `0.06*12 = 0.72`，
而 `Throttle ≥ 0` ⇒ `thrFly` 在 IAS > 71.4 恒为 0（即盘位拉到满也推不出油），而减速板要 IAS>67 才开始动
⇒ **两条区间交叠处油门端已经见底**，物理上不可能"一边加油一边开板"。另外三道保险：
`spdBrk` 顶格 **0.4**（权限实测太大）、**AGL<100 m 一律缴械**（拉平段不许突加阻力）、
零件式用 **`max(spdBrk, Brake)`**（律只能"加"减速板，飞行员随时能压更深 ⇒ 结构上抢不走手动权）。
`gndIdle` 与刹车同用 `airEver` 升空锁 ⇒ 出生/地面滑行仍是飞行员说了算。

**仪器**：Label 39 改成 `thr{...} spd{...}` —— 零件 IC 的值在 HUD/遥测里全不可见，
只有 Label 的 `designText` 能读面板量，这是能量环唯一的观测通道（观测铁律 §30）。

**v2.0 飞行卡**：① 起飞后巡航，看 Label 39 的 `thr` 是否随 IAS 上下动（动 = 油门环活着）；
② 收油下滑制造超速（IAS 拉到 70+），看 `spd` 是否冒头、且 **100 m 以下必须回 0**；
③ 正常进近落一次：目标是五边速度稳定收在 50~60、不再像上局那样越飞越快（76 m/s）。

## v2.3 / v2.4：又一次扎海 —— 真因是**积分门把唯一的积分路掐死**（我先给错了一次诊断）

**现象**（cid=2389 末段，Cochran 22L 五边）：SD 669→448、AGL 20→8、**IAS 钉在 50.9**、`pa` 从 1.1 到 1.2

**我改的那版符号是反的**（进近时 `rate(SD)<0`，前馈应是 `+0.0524·rate(SD)`）。量纲确实要修
（GS 是地速、不是沿跑道轴的接近率，顺风/CRAB 时差 30+ m/s；且旧写法 GS 恒正，符号是"碰巧对"），

**这条门是我为防风车加的，结果在最需要它的工况上把救命的积分关掉了**——典型"保险丝装错位置比没有更致命"。

**数据定案（cid=73802 同会话三次起飞，ta2_flight/日志直读）**：

| 起飞 | 爬升段 pa | 反推积分项 I | 结果 |
|---|---|---|---|
| #1 t=37 | 峰值 11.9 后回落 | ≈ 0 | 冲 112、稳 110 ✅ |
| #2 t=113 | **恒 8.0°** | **≈ −4** | 冲 303、稳 301 ✅ |
| **#3 t=462** | **恒 20.7°**（IAS 58→45） | **≈ +16** | 冲 440+ ❌ |

反推式 `cmdTheF = 0.8·(vsCmdH−vs) + I`：同律同操作，**积分项差 20°**；唯一差别＝第 2→3 遍之间没重开、
`sum()` 不清零 ⇒ **坏起飞 = 带着上一架次的积分残留**。**这是从 2389 到现在的总根**——我前面一直在调"积分门"，
而门管的是"积不积"，治不了"**上一架次的残留**"。

**修法（v2.17）**：给积分器加**退绕支**——门内正常积、门外按时间常数把积分拉回 0：
```
cmdTheF_I = clamp(sum( (|Roll|<0.05 & |Pitch|<0.05 & |vsCmdH|<vsLim-0.5) ? vsErrH*0.35
                                                                        : (0 - cmdTheF_I*1.5) ), -20, 20)
```
门外：地面、大瞬态、失控制 ⇒ **τ≈0.67 s 退绕到 0** ⇒ 落地几秒内清零 ⇒ 下一架次从 0 起（＝与"重开"等价）。
FT 无内置抗饱和，**自参照（引用自身上一帧值）是"把积分拉回 0"的唯一写法**；已在 `ALLOW_SELFREF` 白名单显式放行
（其余自参照仍当错误）。**风险未验**：引擎是否支持 setter 自参照尚未证实（`Context.ResolveVariable` 在编译期绑定，
推理上可行）。**若引擎不收 ⇒ 该 setter 失能 ⇒ 依赖它的 `cmdTheF`/ELE 一并退回原生（飞行员会立刻感到"没增稳"）**；
届时 grep 日志应有 `Invalid expression`/`Variable error`，立刻回退到 v2.16 或改无记忆前馈。

**方法论（终于）**：真正破案的是**用户那句"1→2 重开、2→3 只落地再起飞"**——它把"确定性律"变成"带状态律"，
直接指向 `sum()`。**教训入账：凡是"同一操作、不同次数结果不同"，先找跨架次状态（sum/smooth/锁存），不要去调增益。**

### v2.23.1 建律时又揪出一个**镜像符号 bug**（BG）——先演算后建律的红利
